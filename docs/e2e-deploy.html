Playwright E2E under Bun

Playwright is a third-party tool (pin it: bun add -d @playwright/test@1.48.0 then bunx playwright install chromium). It drives a real browser against your running app.

// e2e/login.spec.ts
import { test, expect } from "@playwright/test";

test("user can log in", async ({ page }) => {
  await page.goto("http://localhost:3000/login");
  await page.fill('input[name="email"]', "alice@example.com");
  await page.fill('input[name="password"]', "secret");
  await page.click('button[type="submit"]');
  await expect(page.locator("h1")).toHaveText("Welcome, Alice");
});
// playwright.config.ts — start the Bun server automatically
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  webServer: {
    command: "bun run server.ts",
    url: "http://localhost:3000",
    reuseExistingServer: !process.env.CI,
  },
});
bunx playwright test              # run E2E suite
bunx playwright test --ui         # interactive UI mode
Playwright runs its own test runner (not bun test). Keep unit/integration tests on bun test and reserve Playwright for browser-level E2E. For headless scraping inside your app, prefer the built-in Bun.WebView — no install.

bun build — bundling

bun build ./src/index.ts --outdir ./dist                # bundle
bun build ./src/index.ts --outdir ./dist --minify        # minified
bun build ./src/index.ts --outdir ./dist --target bun    # for the Bun runtime
bun build ./src/index.ts --outdir ./dist --target browser --splitting  # web
// or programmatically
await Bun.build({
  entrypoints: ["./src/index.ts"],
  outdir: "./dist",
  minify: true,
  target: "bun",
});

Standalone executables — bun build --compile

--compile bundles your app and the Bun runtime into a single self-contained binary — no Bun install needed on the target machine.

# current platform
bun build ./src/cli.ts --compile --outfile myapp
./myapp

# smaller, production binary
bun build ./src/cli.ts --compile --minify --sourcemap --outfile myapp

Cross-compilation

bun build ./src/cli.ts --compile --target=bun-linux-x64   --outfile myapp-linux
bun build ./src/cli.ts --compile --target=bun-linux-arm64 --outfile myapp-arm
bun build ./src/cli.ts --compile --target=bun-darwin-arm64 --outfile myapp-mac
bun build ./src/cli.ts --compile --target=bun-windows-x64 --outfile myapp.exe

Embedding assets

Files you import (or reference via Bun.file with a static path) get embedded into the binary:

import icon from "./icon.png" with { type: "file" };
// icon is a path that resolves inside the compiled binary at runtime
console.log(await Bun.file(icon).bytes());

Dockerizing a Bun app

# Dockerfile
FROM oven/bun:1.4.2 AS base
WORKDIR /app

# install deps first for layer caching
FROM base AS deps
COPY package.json bun.lockb ./
RUN bun install --frozen-lockfile --production

# runtime image
FROM base AS release
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
USER bun
CMD ["bun", "run", "src/index.ts"]
docker build -t my-bun-app .
docker run -p 3000:3000 --env-file .env.production my-bun-app

Production install

bun install --frozen-lockfile --production   # skip devDependencies, fail on lockfile drift
NODE_ENV=production bun run src/index.ts      # run in prod mode
A compiled --compile binary is often the simplest deploy for CLIs and single-service apps: copy one file, run it, no runtime to install. Use the Docker image when you need the full node_modules tree or orchestration.
